# Qwen3.8-35B-A3B-Distill on M4 Pro: bare inference baseline

## Summary

This experiment evaluates **Qwen3.8-35B-A3B-Distill** as a fast, general-purpose local model for VS Code Copilot Chat on Apple Silicon.

The model is a community distillation by Empero: Qwen3.8 teacher behavior distilled into the sparse Qwen3.6-35B-A3B MoE architecture. It has roughly **35B total parameters and ~3B active parameters per token**. It is not an official Alibaba/Qwen Qwen3.8 release.

The local setup used the pinned MLX 4-bit conversion:

```text
HF model: nvythong/Qwen3.8-35B-A3B-Distill-mlx-4Bit
revision: 220dfec3e716bbae93bd66b643e36b2ffe6853ff
local size: ~19.5 GB
```

The result is promising: on an M4 Pro with 48 GB unified memory, the model generated roughly **66-91 tok/s** across ~1K-32K contexts, while prompt processing ranged from roughly **676-951 tok/s**. It also worked through the repository's VS Code Copilot custom endpoint with tool calling enabled and was subjectively interactive enough for real coding work.

This document intentionally describes the **bare baseline** before optional oMLX acceleration features are introduced.

## Why this model

The original repository setup used the dense Qwen3.8-27B 4-bit model. It was capable, but its local latency made interactive coding difficult: direct generation was typically around 14-15 tok/s, and a cold ~9K-token Copilot request could take around 91 seconds end-to-end.

The A3B architecture changes the serving economics. The model stores a much larger sparse MoE, but activates only a small expert subset per token. The working hypothesis was that it could preserve useful general/coding ability while behaving much more like a small active model during inference.

The experiment was designed to answer four questions:

1. Is cold prompt processing fast enough for coding-agent contexts?
2. Is decode fast enough to feel interactive?
3. Does oMLX prefix reuse materially improve repeated Copilot-style requests?
4. Does the model actually work behind VS Code Copilot Chat with tool calling?

## Environment

The successful synthetic run was captured on:

```text
MacBook Pro (Mac16,7)
Apple M4 Pro
14 CPU cores (10 performance + 4 efficiency)
48 GB unified memory
macOS 15.7.4
arm64

oMLX 0.7.0
model context cap for this profile: 32,768 tokens
```

The profile advertises 28,672 input tokens plus 4,096 output tokens to VS Code, keeping the client-side budget inside the 32,768-token experimental cap.

The successful run had exactly one model resident in oMLX during measurement: `Qwen3.8-35B-A3B-Distill-mlx-4Bit`.

## What "bare" means

This is a baseline model/runtime measurement, not a fully tuned oMLX configuration.

The following optional acceleration paths were explicitly disabled:

```json
{
  "mtp_enabled": false,
  "qwen35_ane_prefill_enabled": false,
  "turboquant_kv_enabled": false,
  "qwen35_oq_a8_enabled": false,
  "specprefill_enabled": false,
  "dflash_enabled": false,
  "moe_expert_offload_enabled": false
}
```

Prefix/KV caching and normal oMLX serving were still active. The distinction matters because prefix reuse is part of the real serving behavior we want to measure.

The oMLX status capture also reported the optional `qwen35_prefill` and `decode_fast` custom kernels as unavailable in this installation. Future runs can therefore test both feature toggles and runtime/kernel improvements against a clean reference point.

Synthetic requests ran with model thinking disabled so prefill/decode measurements are comparable. The VS Code profile keeps thinking enabled for real usage.

## Context-scaling results

Two runs were performed at each target context length. The table below reports the aggregate values generated by the benchmark harness.

| Target context | Actual prompt | PP tok/s | TG tok/s | TTFT | TPOT | E2E |
|---:|---:|---:|---:|---:|---:|---:|
| 1,024 | 1,028 | 894.6 | 90.6 | 1.15 s | 11.1 ms | 3.98 s |
| 4,096 | 4,090 | 950.8 | 87.3 | 4.30 s | 11.5 ms | 7.24 s |
| 8,192 | 8,199 | 932.2 | 83.1 | 8.79 s | 12.1 ms | 11.89 s |
| 16,384 | 16,379 | 828.5 | 76.0 | 19.77 s | 13.2 ms | 23.16 s |
| 32,768 | 32,411 | 676.2 | 66.0 | 47.94 s | 15.2 ms | 51.86 s |

The most important interpretation is that **decode remains fast at long context**. Even around 32K the model still produced about 66 tok/s. The dominant interactive penalty is cold prefill: TTFT grows to almost 48 seconds because the model must ingest more than 32K prompt tokens before it can answer.

That diagnosis directly motivates the future prefill-acceleration work.

## Prefix-cache result

The synthetic cache experiment sent two ~8K requests with a large common system prefix and only a small differing suffix.

| Run | Prompt | Cached | PP tok/s | TG tok/s | TTFT | E2E |
|---|---:|---:|---:|---:|---:|---:|
| Cold | 8,189 | 0 | 930.9 | 81.0 | 8.80 s | 10.39 s |
| Warm | 8,188 | 6,144 | 826.4 | 82.1 | 2.47 s | 4.05 s |

The warm request reused 75% of the prompt and reduced TTFT by **3.56x**.

For coding agents this matters more than a synthetic chat benchmark because system instructions and tool schemas repeat across turns. A model that is merely acceptable cold can become genuinely interactive when a large stable prefix is reused.

Raw evidence: [`prefix-cache.md`](../experiments/qwen38-35b-a3b-distill/runs/20261007T195918Z-inference/prefix-cache.md) and [`prefix-cache.json`](../experiments/qwen38-35b-a3b-distill/runs/20261007T195918Z-inference/prefix-cache.json).

## Concurrency and goodput

The concurrency run used an interactive SLO of:

```text
TTFT <= 15 seconds
per-user TG >= 30 tok/s
```

| Concurrent | Aggregate output | p50 TTFT | p95 TTFT | median user TG | peak queued | SLO pass |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 22.5 tok/s | 4.20 s | 4.20 s | 87.6 tok/s | 0 | 1/1 |
| 2 | 21.5 tok/s | 7.31 s | 10.13 s | 54.2 tok/s | 0 | 1/2 |
| 4 | 23.7 tok/s | 18.88 s | 18.94 s | 49.1 tok/s | 2 | 0/4 |
| 8 | 24.9 tok/s | 35.50 s | 35.78 s | 24.0 tok/s | 6 | 1/8 |

This is a useful example of why aggregate throughput is not enough. The machine can keep doing work, but queueing and per-user latency become unacceptable as concurrency rises. For the intended use case -- one developer running a local coding agent -- the single-user result is the important one.

The model-memory telemetry stayed around **19.08 GB** during these runs.

Raw evidence: [`concurrency.md`](../experiments/qwen38-35b-a3b-distill/runs/20261007T195918Z-inference/concurrency.md) and [`concurrency.json`](../experiments/qwen38-35b-a3b-distill/runs/20261007T195918Z-inference/concurrency.json).

## VS Code Copilot Chat result

The model was connected through the repository's inspection proxy using the custom provider template in `config/chatLanguageModels.provider.qwen38-35b-a3b-distill.json`.

Two real Copilot requests were captured with **55 enabled tools**. The tool schemas alone were about **70,942 characters**, and each request contained roughly 23K prompt tokens.

| Request | Prompt | Cached | PP tok/s | TG tok/s | TTFT | Wall time |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 23,465 | 0 | 744.8 | 67.7 | 31.51 s | 33.08 s |
| 2 | 23,365 | 20,480 | 577.9 | 67.9 | 4.99 s | 6.16 s |

The second request reused about **87.7%** of the prompt and cut TTFT by more than six times. This is the practical result behind the subjective observation that the model feels interactive in VS Code despite the very large Copilot prompt.

This capture validates endpoint compatibility, streaming, tool-schema handling, and useful warm-prefix latency. It is **not yet a controlled model-quality benchmark** because the exact coding task was not retained in the privacy-preserving request summaries.

Raw evidence: [`copilot-summary.md`](../experiments/qwen38-35b-a3b-distill/runs/20261007T201306Z-copilot-qwen38-distill-coding/copilot-summary.md) and [`copilot-summary.json`](../experiments/qwen38-35b-a3b-distill/runs/20261007T201306Z-copilot-qwen38-distill-coding/copilot-summary.json).

## Relationship to the old Qwen3.8-27B results

The existing repository measurements for dense Qwen3.8-27B showed approximately 14-15 decode tok/s in direct local tests and much higher cold Copilot latency. The A3B distill is clearly in a different performance class in this setup.

However, the old results and the new inference suite are not a strict apples-to-apples A/B: oMLX version, prompt construction, tool count, workload, and benchmark harness differ. A future publication-quality comparison should run both models through the **same current harness on the same machine** before reporting a precise speedup ratio.

The correct conclusion from this baseline is therefore:

> Qwen3.8-35B-A3B-Distill is fast enough to be genuinely interactive locally, including behind VS Code Copilot Chat, and is the leading fast-default candidate in this repository. The next open questions are quality under repeatable coding tasks and how much additional performance can be extracted from oMLX acceleration features.

## Future performance work

The current numbers should be preserved as the **bare reference run**. The next phase should benchmark optional accelerators independently rather than enabling everything at once.

The most interesting candidates are:

1. **Lightning MTP** -- targets decode by predicting/verifying multiple future tokens. The upstream Empero checkpoint contains MTP weights, but this exact 4-bit MLX conversion must be verified for oMLX MTP compatibility before a speedup is assumed.
2. **Qwen ANE prefill / optional Qwen prefill kernels** -- directly target the cold-prefill bottleneck identified by the 16K/32K measurements.
3. **TurboQuant KV** -- primarily interesting for KV-cache memory, long context, and concurrency; it must be benchmarked rather than assumed to improve speed.
4. **Qwen oQ A8** -- a model-specific quantized execution path that needs quality and long-context validation.
5. **SpecPrefill and DFlash** -- speculative paths that may reduce latency when a compatible draft setup is available.
6. **MoE expert offload** -- primarily a memory-headroom trade-off rather than a default performance optimization on a machine where the 4-bit model already fits comfortably.

The planned methodology is documented in [`inference-engineering.md`](inference-engineering.md). The rule is simple: change one feature, rerun the same suite, record the result, and only combine features after their individual effect is understood.

## Reproducing the baseline

Select and set up the profile:

```bash
./scripts/setup-qwen38-distill.sh
```

Start the local stack:

```bash
./scripts/start.sh
./scripts/status.sh
```

Run the synthetic inference suite:

```bash
./scripts/run-inference-benchmarks.sh
```

For Copilot Chat, merge:

```text
config/chatLanguageModels.provider.qwen38-35b-a3b-distill.json
```

into VS Code's custom Language Models configuration, select **Qwen3.8 35B-A3B Distill MLX**, and use the experiment capture wrapper when a repeatable coding workload is ready:

```bash
./scripts/copilot-experiment.sh start qwen38-distill-coding
# use Copilot Chat
./scripts/copilot-experiment.sh finish
```
